# Security review of supplied .NET 10 backend — release blockers

These findings come from the backend source ZIP and updated Swagger OpenAPI text. They **do not claim a running production server is configured identically**, nor do they imply an exploit was performed.

**Do not connect real Amazon production credentials until the backend team verifies and remediates these controls.**

## Requested security contract changes

**Auth/session:** Login returns a non-token response and sets `HttpOnly; Secure; SameSite=Lax; Path=/` cookie. Add `/api/security/csrf` (proposed endpoint) that emits a non-secret `XSRF-TOKEN` cookie bound to session; all mutating requests validate the `X-XSRF-TOKEN` header. Session revocation and MFA needed.

**Account access:** Introduce `UserVendorAccess`, plus `GET /api/vendor-accounts/accessible` and administrator endpoints for assigning accounts, or equivalent endpoints. Current `GET /api/vendor-accounts` returns all accounts to every authenticated user.

**Amazon authorization:** Current Swagger doesn't expose public LWA authorization start/callback/connection status endpoints. Implement them on the server for each vendor authorization or document the existing private consent flow. Keep Amazon refresh tokens and LWA secrets out of the browser.

**Deployment:** Prefer HTTPS same-origin architecture. Restrict Swagger UI to development/admin environments; use a host-based CSP and strict response headers.

**Integration update, November 7, 2026:** At the user's request, the frontend now connects all supplied Swagger operations, including credential changes, confirmed account deletion, local purchase-order acknowledgments, and bulk uploads. Administrator controls are restricted in the UI. The backend findings above remain separate server work; the Angular XSRF client cannot create server-side antiforgery validation. Browser integration tests use isolated fixtures and do not submit real credentials or mutate hosted business data.
